# 抽象优先建模

AI Agent 最大的风险不是写出不能运行的代码，而是写出"看起来能运行但破坏了系统边界"的代码。抽象优先建模通过强制先定义契约再实现，从根本上消除这类风险。

> DDD 战略+战术建模（限界上下文、聚合、领域事件等）详见 `ddd-modeling.md`。本文件聚焦 ACL 翻译、契约优先、组合/多态等通用工程原则。

## 通用原则

### ACL 翻译层

每个需求进入实现之前，必须经过三层翻译：

```
口头需求 → [ACL 翻译] → 领域模型（OO 契约）→ 具体代码
```

- **A (Abstraction)**：将需求提炼为稳定的抽象概念
- **C (Contract)**：定义接口、DTO、领域对象之间的契约关系
- **L (Logic)**：在契约约束下实现具体逻辑

### 契约优先的编码顺序

这不是建议，是**强制顺序**：

1. **先写契约**：在所属模块定义接口 / 抽象类 / DTO（不写实现）
2. **展示确认**：将设计呈现给审查者，确认符合单一职责和开闭原则
3. **后写实现**：面向接口编写具体类，保持最小化和局部化

违反这个顺序的后果：具体实现会反向塑造接口设计，导致耦合、泄漏和难以测试。

### 组合优于继承

**规则：继承深度 ≤ 1。** 如果需要更深层次，用组合 + 依赖注入替代。

为什么对 AI Agent 特别重要：
- AI 倾向于生成深层继承树（训练数据中常见"
- 深层继承让变更影响范围不可控
- 组合让每个组件可独立测试、替换、理解

**做法：**
- 用 `@Autowired` / DI 容器注入依赖，而不是 `extends`
- 小接口、小类、明确职责
- 如果类名中出现 "Base" 或 "Abstract" 超过一层，重新设计

### 多态优于分支

**规则：嵌套 if/else ≥ 2 层或 switch ≥ 3 分支 → 使用 Strategy/Factory/Handler 模式。**

为什么对 AI Agent 特别重要：
- AI 天然擅长生成 if/else 分支代码
- 分支代码容易通过测试但难以扩展
- 每新增一个条件，已有分支的风险增加

**做法：**
- 2+ 层嵌套：提取 Strategy 接口 + 多个实现
- 3+ switch 分支：使用 Factory 模式或 Handler 注册表
- 用 Map<Type, Handler> 或 Spring 的 `List<Interface>` 自动注入代替 switch
