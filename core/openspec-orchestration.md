# OpenSpec Integration

OpenSpec owns the change lifecycle. Engineering is a governance wrapper that
calls native OpenSpec operations through the agent's generated Skills. There is
no dispatcher, parent-child lifecycle contract, or Harness-owned state.

## Native operations

Use the project-local Skills generated by `openspec init`:

- `openspec-explore`
- `openspec-propose`
- `openspec-apply-change`
- `openspec-sync-specs`
- `openspec-archive-change`
- `openspec-update-change`
- `openspec-verify-change`

Use the CLI for status, instructions, validation, context, templates, and schema
inspection. `openspec validate --strict` is the authoritative artifact-structure
check; `openspec-verify-change` checks implementation completeness, correctness,
and coherence against the artifacts.

## Governance attachment

OpenSpec creates the change directory and `.openspec.yaml`. Engineering then runs:

```bash
openspec new change <change-id> --schema harness-engineering
python3 docs/methodology/scripts/init_governance.py <change-id> \
  --title "..." --mode backend --owner <actor> \
  --trigger native-selection
```

`check_change_workspace.py` rejects live changes without the `harness-engineering`
marker contract and a valid `governance.json`. It does not block native OpenSpec
commands.

## Task evidence

The custom `harness-engineering` schema keeps OpenSpec's `tasks.md` checkbox
format and adds governance instructions. During Apply, record one run per checked
task in `execution-evidence.json`; `check_execution.py` verifies coverage,
commands, changed files, timing, and integration order.
