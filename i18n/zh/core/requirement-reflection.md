# 需求反思与澄清

需求反思是回答级质量门。在形成任务回答草稿后、发送回答或产生副作用前，Agent 必须检查自己是否已经足够准确地理解用户目标，才能继续行动。这是结论检查，不要求暴露模型的私有思维链。

## 决策结果

使用以下结果之一：

| 结果 | 判断条件 | Agent 行动 |
|---|---|---|
| `ready` | 目标、范围、完成标准、约束和授权已经足够明确 | 说明重要假设，在授权范围内回答并执行 |
| `clarify` | 歧义可能改变实现、结果、成本、安全性或验证方式 | 停止写入和外部副作用；提出聚焦问题并给出推荐选项 |
| `correct` | 需求与仓库事实、已声明约束或技术不变量冲突 | 展示证据和冲突；给出最小可行修正；确认后才能采用修正后的理解 |
| `blocked` | 缺少授权、证据或安全决策，无法继续 | 说明阻塞点、所需负责人或证据，并给出最安全的下一步方案 |

不要在多个实质不同的解释之间静默选择。没有状态变更的可逆解释可以列出明确标注的替代方案；但只要歧义会影响实现或其他有后果的操作，就必须等用户确认。

## 反思清单

针对回答草稿检查：

- **意图**：用户想为谁、为什么达成什么结果？
- **范围**：包含哪些文件、系统、用户、环境和明确排除项？
- **验收**：什么可观察结果能证明工作正确或完成？
- **约束**：有哪些技术、兼容性、安全、数据、时间或流程约束？
- **证据**：哪些事实来自仓库或工具，哪些只是推断？
- **一致性**：需求是否与现有契约、策略、依赖或客观可行性冲突？
- **授权与风险**：Agent 是否被授权执行该操作？是否可能造成不可逆或高影响变更？

不需要追问每个缺失细节，只追问会改变计划、行为、安全性或完成结论的细节。将相关问题合并；可能时每次最多提出三个阻塞问题。

## 澄清回答格式

结果为 `clarify`、`correct` 或 `blocked` 时，按以下顺序回答：

1. **当前理解**：用一到两句话概括目标结果。
2. **发现的问题**：准确指出歧义、冲突、缺少授权或证据缺口。
3. **依据**：引用相关仓库事实、约束或未知项，不能把假设说成事实。
4. **最佳方案**：给出推荐选项、取舍和简短可执行计划。
5. **请确认**：提出能让用户选择或确认推荐方案的最小问题。

在获得确认前，不得把推荐解释当成已批准需求，不得修改有后果的文件，也不得声称完成。用户确认了变更后的需求后，更新任务计划并重新执行本反思，再继续工作。

## 需求明确时的回答

结果为 `ready` 时，简要说明需求、重要假设、计划和验证方式，然后在确认范围内回答或执行。如果后续证据推翻了当前理解，应回到 `correct` 或 `blocked`，而不是为之前的回答辩护。

## 与 Self-Refine 的关系

需求反思判断 Agent 应该行动还是向用户提问；Self-Refine 在范围已经理解后，检查草稿、设计或实现质量。二者都遵循有界反馈原则，但都不能审批契约、替代确定性门禁或授权受保护路径和生产变更。
