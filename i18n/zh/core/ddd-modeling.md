# 领域驱动设计建模 (DDD Modeling)

AI Agent 在面对复杂业务时最容易犯的错误是跳过建模直接写 CRUD。结果是代码"能跑"但业务概念散落在 Service、Controller、SQL 里，任何规则变更都要满仓库追改。DDD 提供了一套从战略到战术的建模语言，让领域知识在代码中有稳定落脚点。

本文件是技术栈无关的通用方法论。项目特定的映射（哪些模块对应哪些上下文、哪个类是聚合根）应写在项目自身的入口文档（如 CLAUDE.md）中，不在此重复。

## 通用原则

### 战略设计

战略设计回答"系统如何被切成相互独立的部分"。先做战略、后做战术，顺序不可颠倒。

#### 统一语言 (Ubiquitous Language)

- 业务专家、产品、开发使用同一套词汇描述领域，且这套词汇**直接出现在代码标识符中**
- 命名时拒绝技术化翻译：业务说"调度单"，代码就叫 `DispatchOrder` 而非 `TaskItem` 或 `BizData`
- 统一语言一旦在上下文内确立，所有产物（类名、字段名、API、SQL、文档）必须使用它
- 同一个词在不同上下文可以含义不同——这是边界而非冲突

#### 子域划分

把业务拆成三类子域，决定各自的投入策略：

| 类型 | 识别特征 | 投入策略 |
|------|----------|----------|
| 核心子域 | 业务差异化竞争力所在，最复杂、最常变 | 自研、最优建模、最严测试 |
| 支撑子域 | 业务必需但非差异化点，定制化存在 | 自研但保持简单，或定制化封装 |
| 通用子域 | 行业通用、可买到现成方案 | 采购 / 开源 / 标准实现，不为差异化投入 |

判断顺序：先识别核心子域（一句话能说出"我们的竞争力是 X"），再把剩下的归类。

#### 限界上下文 (Bounded Context)

- 一个限界上下文 = 一套完整且自洽的领域模型 + 一个团队的所有权边界
- 边界内的统一语言、模型、数据模型必须一致；边界外不强制一致
- 边界 ≈ 模块边界 ≈ 物理部署边界（单体中是模块/包，微服务中是服务）
- 一个子域可以对应一个或多个限界上下文；先按团队规模和模型复杂度划，再按性能/部署需求调

#### 上下文映射 (Context Map)

上下文之间必然交互，映射描述交互关系。常用模式：

| 模式 | 关系 | 适用 |
|------|------|------|
| 共享内核 (Shared Kernel) | 两个上下文共享一部分模型，改它要双方同意 | 团队紧密协作、共享稳定核心 |
| 客户-供应商 (Customer/Supplier) | 供应商优先考虑客户需求，但有权谈条件 | 上下游团队、有协商机制 |
| 遵奉者 (Conformist) | 客户被迫遵循供应商模型，无协商权 | 上游模型庞大且不为自己定制 |
| 防腐层 (ACL, Anti-Corruption Layer) | 客户建翻译层隔离上游模型污染 | 集成遗留/外部系统、保护核心 |
| 公开主机服务 (OHS, Open Host Service) | 供应商对外暴露标准化协议 | 一个供应商被多个消费者使用 |
| 各行其道 (Separate Ways) | 上下文之间无集成 | 模型差异大、集成成本高于价值 |

防腐层是 AI Agent 最该掌握的模式——它把"外部模型翻译成本上下文模型"显式化为代码，而不是让外部概念悄悄渗透进来。

### 战术设计

战术设计在限界上下文内部，提供建模积木。

#### 实体 (Entity)

- 有唯一标识，身份不依赖属性
- 属性可变，但 ID 不变
- 包含属于它的行为（方法），不只是数据容器
- 判别：两个属性全相同但 ID 不同的实体是两个对象

#### 值对象 (Value Object)

- 无唯一标识，由属性值定义身份
- 不可变 (immutable)，所有字段 final
- 可安全共享、可作字典 key
- 判别：两个属性全相同的值对象是同一个对象
- 优先用值对象而非基本类型：`Money(amount, currency)` 而非 `BigDecimal amount + String currency`

#### 聚合与聚合根 (Aggregate & Aggregate Root)

聚合是一组紧密关联的对象，对外作为一个一致性边界：

- 每个聚合有一个根实体（聚合根），外部只能持有根的引用
- 跨聚合引用**只通过 ID**，不持有对方对象引用
- 聚合内强一致：单次事务只修改一个聚合
- 聚合间最终一致：通过领域事件异步同步
- 聚合要小：不要把整个对象图塞进一个聚合，宁可拆小再靠 ID 关联
- 根实体负责维护聚合内不变量 (invariants)，所有变更入口走根的方法

#### 领域服务 (Domain Service)

- 承载**不属于任何一个实体/值对象**的领域逻辑
- 无状态
- 与应用服务的区别：领域服务里是业务规则，应用服务里是流程编排（事务、安全、调度领域服务/仓储）
- 命名应该是业务术语（`PricingService`），不是技术术语（`PriceHelper`）

#### 应用服务 (Application Service)

- 编排用例：接外部请求 → 加载聚合 → 调用领域方法 → 持久化 → 发布事件
- 不含业务规则，业务规则下沉到实体/领域服务
- 控制事务边界和安全
- 接口以用例命名（`submitOrder` / `DispatchOrderUseCase`），DTO 与领域对象分开

#### 仓储 (Repository)

- 为聚合根提供持久化抽象，看起来像"内存中的集合"
- 接口属于领域层，实现属于基础设施层
- 一个聚合根一个仓储，不要为非根实体单独建仓储
- 仓储返回的是聚合根实体（或其快照），不是 DataTable / Record

#### 领域事件 (Domain Event)

- 描述"过去发生的、对业务有意义的事实"，命名用过去时（`OrderPlaced`、`DispatchCompleted`）
- 由聚合根或领域服务在状态变更后发布
- 发布方不关心谁消费——这是解耦点
- 跨聚合最终一致性靠事件，不靠分布式事务

#### 工厂 (Factory)

- 当聚合构造逻辑复杂或需要保证不变量时，用工厂封装创建
- 简单构造直接 new / builder 即可，不必强行引入工厂
- 工厂可以是一个静态方法、一个独立的 Factory 类，或聚合根上的工厂方法

### 建模纪律

| 规则 | 反例 |
|------|------|
| 跨聚合只通过 ID 引用 | 聚合 A 持有聚合 B 的对象引用并直接调用其方法 |
| 聚合内强一致、聚合间最终一致 | 一个事务里改两个聚合根 |
| 实体不承担数据访问职责 | 实体方法里直接写 SQL / 调 Mapper |
| 命名跟随统一语言 | `UserInfo` / `TmOrder` / `BizData` |
| 领域对象不依赖基础设施 | 实体 / 值对象 import 框架的 `@Service`、`@Component` |
| 应用服务不含业务规则 | 在应用服务里写价格计算、风控规则 |
