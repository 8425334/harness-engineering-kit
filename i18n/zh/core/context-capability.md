# 上下文能力与提示词缓存

上下文能力是保持模型上下文窗口精简、相关、可持久且低成本复用的工程纪律。本文讲解两条关联的思想：**提示词缓存前缀不变式**——基于 docs 的方法论为何能达到 ~99%+ 的缓存命中率——以及工程化上下文能力的**五维模型**。

## 通用原则

### A. 提示词缓存前缀不变式

LLM 提示词缓存（Anthropic 服务端缓存）是**字节级精确的前缀匹配**。缓存 key 由渲染后提示词到每个 `cache_control` 断点为止的确切字节决定。前缀中任何字节变化都会使其后所有内容失效。渲染顺序为 `tools → system → messages`。

```
[ tools ][ system ][ messages 1..n ]          ← 字节级精确前缀
      └────────────────┬────────────────┘
此处任何字节变化 → 其后全部被重新计算（缓存未命中）
```

在 agentic 编码循环中，每一轮请求几乎与上一轮完全相同：整段既有对话加上一小块新增增量（Δ，即新增的回复与工具结果）。因此单轮命中率为：

```
命中率 ≈ (总输入 − Δ) / 总输入
```

随对话增长逼近 100%——**前提是前缀永不被重写**。

基于 docs 的方法论通过三个特性保持前缀稳定：

| 机制 | 保持了什么 | 为何能避免缓存未命中 |
|-----------|-------------------|------------------------------|
| 冻结 system prompt | CLAUDE.md / AI.md 被确定性地、版本化地加载 | 每轮 system prompt 字节一致 → 从第一轮起就命中 |
| 低上下文搅动 → 罕见 compaction | 未被压缩的对话前缀 | compaction / 摘要会重写历史 → 缓存全量失效；docs 即地图，读取定向、增量小 |
| 工作流确定化 | 可预测的工具调用序列 | 更少、更聚合的工具调用落在缓存断点可遍历的 20-block 回看窗口内 |

缓存经济性：会话级命中率为 `cache_read / (input + cache_creation + cache_read)`；余量即每轮的新增增量。缓存读取约按全价输入的 0.1× 计费，因此 ~99% 的命中率意味着成本与延迟主要由廉价的缓存读取构成。

### B. 五维上下文能力模型

| # | 维度 | 助记 | 解决的问题 |
|---|------|------|-----------|
| 1 | 窗口与压缩 | 装得下 | 上下文放不下 |
| 2 | 跨会话记忆 | 记得住 | 上下文跨会话丢失 |
| 3 | 注入精度 | 装得准 | 上下文过宽而无效 |
| 4 | 缓存效率 | 用得省 | 上下文反复以全价重算 |
| 5 | 每 token 推理深度 | 想得深 | 每个 token 的产出质量 |

#### 1. 窗口与压缩（装得下）

窗口必须装得下工作。尽量使用大窗口模型；窗口将满时让 harness 压缩；当问题是过期内容时，优先**上下文裁剪**（清除过期的工具结果与已完成的思考块）而非摘要——裁剪是修剪，摘要是重写。见 `harness-engineering.md` 组件 5 的压缩保持模式，它让进行中的一轮在压缩事件后依然存活。

#### 2. 跨会话记忆（记得住）

持久化必须跨会话存活的内容：事实进入持久记忆系统；进行中的一轮进入 round contract（`harness-engineering.md` 组件 5，部署件在 `templates/compaction/`）；长期决策放进 plans 与 specs（`mandatory-skills.md` — OpenSpec、Superpowers）而非占用上下文。原则：明天仍需要知道的东西应该是文件，而不是对话。

#### 3. 注入精度（装得准）

装入对的上下文，且不多装。路径文档给 agent 一张地图；codegraph 提供符号级检索而非整文件 dump（`mandatory-skills.md`）；子代理充当压缩器——广读、只回结论；skills 懒加载正文；tool search 只加载相关的 schema。每少装进窗口的一个字节，都是不需要反复重算的一个字节。

#### 4. 缓存效率（用得省）

上下文装入后，让复用变便宜。冻结 system prompt（docs 确定性、版本化）。会话中途绝不重写顶层 system prompt——改用中途 system 消息追加：

```json
{"role": "system", "content": "更新：订单服务边界已定稿"}
```

用 `max_tokens: 0` 预热；流量有间隙时选 1 小时 TTL；每轮工具调用 block 控制在 ~15 个以内，让缓存断点落在 20-block 回看窗口内；会话中途不更换模型或工具（缓存按模型与工具隔离）。

#### 5. 每 token 推理深度（想得深）

在固定预算内让每个 token 产出更多：adaptive thinking 加 effort 分层，让模型在关键处想得更深；结构化输出让回复紧凑可复用；programmatic tool calling 在沙箱里跑流水线，只有最终输出回到窗口。
