# 任务图与并行执行

并行执行是 Apply 阶段的一项能力，不是第二套生命周期。Design 必须把已审批变更整理为确定性任务图：任何平台都能顺序执行；只有 Agent 运行时和仓库隔离条件都安全时才并发执行。

## 审批绑定的任务图

`task-plan.json` 是受审批绑定的父级 DAG；`tasks.md` 是 OpenSpec 的人工可读子级投影，任务 ID 和顺序必须一致。它在 Design 时必须全部未勾选，Approval 后复选框成为运行态进度。任务描述、依赖、范围、验收和验证仅以不可变 DAG 为权威。每个任务必须声明：

- 稳定的 `T<number>` ID、类型、标题和依赖 ID；
- 不含 glob 的显式项目相对 `write_scope`；
- 形成有界 Worker Brief 所需的 Design/Spec 引用；
- 可观测验收条件和精确的局部验证命令；
- 该任务是否允许并发。

任务数组与 `integration.merge_order` 都必须满足拓扑顺序。两个相互独立、允许并发的任务不得有重叠写范围；范围重叠时必须通过依赖关系串行化。`check_task_plan.py` 确定性校验这些不变量并输出执行波次。

Approval 后修改依赖、范围、契约引用、验收条件、验证命令或合并顺序都属于契约漂移，必须进入 `CONTRACT_CHANGED`；运行时换 Agent 或重试只属于执行证据，不构成漂移。

## Apply 协调者

唯一协调者负责生命周期状态、调度、集成和最终验证。协调者判断当前 Agent 平台是否支持并发 Worker，以及是否具备安全隔离：

1. 优先为每个 Worker 使用独立分支/工作树。只有平台能可靠协调写入时，才允许在同一工作区使用互不相交的写范围。
2. 只调度当前就绪波次中依赖已完成的任务；不可并发任务是屏障，必须单独执行。
3. Worker 只接收自己的任务、契约引用、已解析的路径上下文、写范围、验收条件和局部验证命令。
4. Worker 不得推进生命周期、编辑审批产物、扩大范围、集成他人工作或宣告整个变更完成。
5. 每个任务的聚焦验证成功后，协调者调用 `record_task_completion.py complete <change-dir> <task-id> --run <task-run.json>`；该操作记录 run 并自动勾选对应 OpenSpec task。
6. 协调者按已审批合并顺序集成成功结果、解决冲突，并重新执行全部已审批最终验证命令。

如果并发 Worker 或安全隔离不可用，协调者按同一任务图顺序执行，并记录明确降级原因。缺少并行能力不能减少任务、审批或门禁。

## 执行证据

`execution-evidence.json` 记录实际策略与能力、协调者、时间窗口、每个任务的完成记录、隔离/工作区、改动文件、提交/差异或共享工作区结果引用、局部命令结果、冲突解决、集成顺序和最终验证。只有证据显示不同执行者在工作树或不相交范围隔离下存在重叠执行区间，才能声明并行执行。

集成前，每个改动文件只能有一个任务 Owner，且必须位于已审批写范围内；最终还必须进入 Review 摘要。协调者可以在集成时修改已审批范围内文件，但必须记录。若执行文件集合与 `review-evidence.json` 不完全一致、任一已审批任务缺少成功执行记录，或 `tasks.md` 已勾选 ID 与成功 run 不完全一致，Review 必须失败。`sync` 只允许从执行证据修复复选框投影，不能反向生成证据。
