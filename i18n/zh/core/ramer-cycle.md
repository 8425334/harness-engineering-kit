# RAMER 循环

RAMER 是 AI 辅助开发的强制工作流。在任何非 trivial 代码变更之前，必须完成这五个阶段。

> **自动化执行**：RAMER 已实现为全自动 Agent 系统（`/ramer` skill）。详见 `ramer-agent.md`。本文件定义 RAMER 的**原则和阶段内容**；ramer-agent.md 是**自动化执行层**。

## 通用原则

```
[R] READ → [A] ANALYZE → [M] MODEL → [E] EXECUTE → [R] REVIEW
```

### R — READ（读取上下文）

在修改任何代码之前，先加载目标路径的上下文文档。AI Agent 不能依赖训练数据中的猜测 — 必须从当前仓库获取真实约束。

**做什么：**
- 读取目标目录的路径文档（AI.md / ai.json）
- 读取父目录的路径文档，逐级向上直到根目录
- 提取职责边界、依赖约束、禁止事项
- 识别受影响的模块和跨模块关注点

**不做什么：**
- 不要跳过文档直接看代码
- 不要假设"类似项目"的惯例就是当前项目的惯例

### A — ANALYZE（分析边界）

理解需求、现有代码和模块边界。识别变更类型（新功能 / 修改 / 修复），确定受影响模块和跨模块依赖。

**做什么：**
- 确定变更类型和影响范围
- 识别跨模块协调点（需要 Domain Events？需要接口？）
- 判断是否需要走完整 SDD 流程还是可以快速修复

**不做什么：**
- 不要在不清楚边界的情况下开始设计
- 不要把局部修复扩展为无关的重构

### M — MODEL（抽象建模）

**这是 RAMER 最关键的一步。** 永远不要从具体实现开始。先将需求通过抽象层翻译：

```
口头需求 → [ACL] → 领域模型（OO 契约）→ 多模块代码
```

**固定编码顺序（契约优先）：**
1. 在所属模块定义接口 / 抽象类 / DTO
2. 展示设计，等待确认（确保符合单一职责 & 开闭原则）
3. 确认后才实现具体类（面向接口编程）

**两条铁律：**
- **组合优于继承**：继承深度 ≤ 1，优先 DI + 组合
- **多态优于分支**：嵌套 if/else ≥ 2 层或 switch ≥ 3 分支 → Strategy/Factory/Handler

### E — EXECUTE（执行实现）

严格依据已确认的契约实现具体类。保持变更最小化和局部化。

**做什么：**
- 面向接口编程
- 只修改当前任务需要的内容
- 遵循项目现有模式和命名约定

**不做什么：**
- 不扩大影响范围
- 不混入无关重构
- 不因为"方便"而破坏已有的稳定结构

### R — REVIEW（回顾验证）

运行质量门禁，验证边界合规，检查一致性。

**做什么：**
- 运行 fitness gate（至少 `--tier fast`）
- 验证模块边界未被破坏
- 检查 Mapper/XML/Entity 三方一致性（如适用）
- 确认路径文档是否需要同步更新
